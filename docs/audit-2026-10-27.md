## 一、摘要與總體判定

### （一）三句結論

1. **這個項目的功能完成度與單元測試紀律，高於同規模個人 Android 項目的平均水準**：207 個 JVM 測試全部通過、主題層有 WCAG 對比度守衛與高對比度調色盤、憑據以 AndroidKeyStore AES-GCM 加密、WebView 關閉檔案存取、`allowBackup=false`。這些不是偶然，是有意識的工程投入。
2. **但「可交付」與「可發佈」之間仍有一條未跨過的鴻溝**：交付 APK 用公開的 Android Debug 金鑰簽章（本次以 `apksigner` 實測確認）、無 CI、無靜態分析、無覆蓋率門檻、依賴無鎖定與完整性驗證、建置環境靠文檔口耳相傳（用系統默認 JDK 17 直接構建會失敗）。任何一次重裝系統或換機器，都無法保證構建出位元相同的產物。
3. **代碼層面的缺陷集中在三類**：「上游內容或網絡異常時靜默失敗」（漫畫源空列表、論壇分欄錯位、代理 token 外送）、「無上限或非原子資源使用」（離線快取無配額、帖子快取計量錯誤、直播 MutationObserver 樣式風暴、Huavod single-flight 競態）、「無障礙與對比度的硬性缺口」（26 dp 觸控目標、底欄無選中語義、白字壓珊瑚色 3.15:1）。直播源選擇已移至「我的設置」，核對後確認入口與回調存在，不列為缺陷。

#### H-05 `ForumPostCache` 以條目數計量、單條上限 400 萬字元 → 理論峰值約 256 MB【靜態核對】

- **位置**：`data/forum/ForumPostCache.kt:20-28`、`:39-42`、`:63-73`
- **證據**：

```kotlin

```

#### H-06 哔咔分頁 `do…while` 無頁數上限、迴圈內阻塞不可取消【靜態核對】

#### H-09 直播頁 MutationObserver 監聽整頁，每條聊天訊息都重跑整套樣式改寫【靜態核對】

- **位置**：`ui/LiveScreen.kt:2327-2338`（觀察器安裝）、`:2116-2320`（`applyPlayerStage`）、`:2242-2293`（`style.setProperty(..., 'important')` 區塊）


#### H-10 MulticastLock 單欄位競態，stop／re-start 會洩漏已持有的鎖【靜態核對】

- **位置**：`cast/SsdpDiscovery.kt:30`、`:200-219`；`cast/CastManager.kt:82-94`、`:98-102`
- **證據**：


#### H-11 Media3 離線快取無配額、無淘汰器、無剩餘空間檢查【靜態核對】

- **位置**：`data/OfflineCacheManager.kt:110-118`（`SimpleCache(..., NoOpCacheEvictor(), ...)`）、`:121-127`（`maxParallelDownloads = 2`）、`:172-215`（`enqueue` 無前置空間檢查）
- **證據**：

```kotlin

    File(applicationContext.filesDir, CACHE_DIRECTORY),   // "offline_media"
    NoOpCacheEvictor(),                                   // 永不淘汰
    databaseProvider,
)
```

- **可達性**：用戶每次在播放器點「緩存」即新增一個完整下載；`NoOpCacheEvictor` 只在顯式 `removeDownload`／`removeAllDownloads` 時刪除，應用層沒有總量配額，也沒有 enqueue 前的剩餘空間檢查。單部 1 小時 1080p 影片約 0.8–1.5 GB。
- **影響**：離線快取可無限增長直至寫滿裝置儲存；寫滿後其他應用與系統更新失敗，且 `filesDir` 空間不足時 Media3 下載以不明錯誤中斷，用戶難以歸因。

## 五、低危與技術債（26 條）

### （一）安全（6 條）

- **L-01** `LiveScreen.kt` 子框架放行任意 http(s)，JS 橋對所有 frame 可見（能力僅 `onVideoSize(int,int)`，影響有限）。建議只對主 frame 掛橋並限制子 frame 域名。
- **L-02** `data/comic/EhentaiDns.kt` 硬編碼 IP，繞過系統 DNS；TLS 仍驗證故不能直接劫持，但機房一變即全站不可用。建議保留系統 DNS 為主、硬編碼為 fallback。
- **L-03** `LocalMediaProxy` 的 Range 解析不完整（不支援 `bytes=-N` suffix 與多段），206 邊界不嚴格。建議按 RFC 7233 補齊或明確回 200。
- **L-04** HLS 重寫以客戶端 `Host` header 組裝代理 URL；惡意 Host 可令清單指向第三方（需已持 token）。建議以實際綁定位址生成。
- **L-05** `res/xml/data_extraction_rules.xml` 只排除 root／sharedpref，未排除 `files`（離線媒體）／`database`（Media3 DB）／`external`。建議補齊。
- **L-06** 未設 `FLAG_SECURE`：最近任務縮圖與屏幕錄影可捕捉成人內容。建議提供「私密模式」開關，開啟時對播放器與漫畫閱讀器設 `FLAG_SECURE`。

### （二）數據層（6 條）

- **L-07** `PlaybackResolver.kt:106-113,124-131` 預取失敗只記耗時，丟棄異常物件，無法診斷長期失敗。
- **L-08** `data/comic/JmComicSource.kt` 多域名輪詢為 failover 非重試，域名表硬編碼且無 TTL；黑名單域名會每次重試。
- **L-09** `data/forum/ForumImageSaver.kt:94` 以 server `Content-Type` 為準；`text/html` + `.jpg` 結尾會被當成圖片存入相冊（無害但污染）。
- **L-10** `AppPreferences.kt:206-209` 快取上限（30/120/30/30）以「條目」為單位，未限制單條 JSON 大小；論壇帖正文若超長仍可能令 SP 檔達數百 KB。
- **L-11** `data/VideoRepository.kt:130-140` 全局搜索以 `views = "$source · ${views}"` 承載來源名，語義污染：排序、格式化、未來分析都會踩坑。建議 `VideoItem` 加 `sourceName` 欄位。
- **L-12** `data/VideoRepository.kt:565` Beeg 用純數值 `fileId` 作 `id`，與 91Dongman 的數值 id 在跨源聚合時可能碰撞而被 `distinctBy` 丟棄。建議 id 一律 `源前綴:原始id`。

### （三）效能（6 條）

- **L-13** `data/OfflineCacheManager.kt:121-127` 固定 2 執行緒下載，但無分片併發與 Wi-Fi only 開關提示。建議評估 Media3 分片併發與網絡策略。
- **L-14** `ui/CoverCache.kt:8-9` 記憶體 24 MB＋磁碟 96 MB，加上 Coil 64 MB＋128 MB，圖片快取合計約 88 MB 記憶體（256 MB heap 裝置約 34%）。建議統一由 Coil 管理，移除重複層。
- **L-15** `ui/AuroraViewModel.kt` `allKnownVideos` 無界增長，每次分頁整表複製 + `distinctBy`（O(n²) 累積）。建議以 `LinkedHashMap` 增量維護。
- **L-16** `LiveScreen.kt:1800-1802` 彈幕去重集合無上限；`LiveScreen.kt:1077-1081` 每條新評論強制滾到底。建議去重集合改 LRU。
- **L-17** `ui/CoverImageLoader.kt:39-46`、`cast/CastManager.kt:37-40`、`AuroraApplication.kt:41-49` 三個獨立 `OkHttpClient` 各自持有連線池與執行緒。建議共用一個 client（不同 interceptor）。
- **L-18** `ui/CoverPrefetch.kt:203-221`、`AuroraViewModel.kt:358-359` 進程級去重表無上限。建議加 LRU 上限。

### （四）UI（4 條）

- **L-19** `ui/AppComponents.kt:874-886` `NetflixSectionHeader` 的「全部」文字點擊區約 26 dp。建議加 `minimumInteractiveComponentSize()`。
- **L-20** `ui/HomeScreen.kt:486-694` hero 整卡可點，內含「播放／我的片單／詳情」三個子按鈕；輔助技術下出現嵌套可點區域。建議整卡不可點，只保留子按鈕。
- **L-21** 未接入 Predictive Back（`docs/ui/design-system.md:6` 明列基線，`grep PredictiveBackHandler` = 0）。建議 `android:enableOnBackInvokedCallback="true"` + `PredictiveBackHandler`。
- **L-22** `LiveScreen.kt:1793-1853` 彈幕層與 `NativeSitePlayer.kt:388-444` 進度條為自訂繪製，無語義。建議加 `progressBarRangeInfo` 與 `semantics { invisibleToUser() }` 到裝飾層。

### （五）構建與倉庫（4 條）

- **L-23** `CHANGELOG.md` 76 KB、49 條、兩種標題格式、缺 2.5.0。建議拆分為 `CHANGELOG.md`（最近 10 版）+ `docs/changelog-archive.md`。
- **L-24** 倉庫衛生：根目錄與 `dist/` 共 3 個 `.DS_Store`（已 ignore 但存在）、`.kotlin/` 未列入 `.gitignore`、`dist/SHA256SUMS` 35/38 條失效、`.git` 無 pack（2,985 loose object）。建議 `git gc --aggressive`、補 `.kotlin/`。
- **L-25** 未設 `abiFilters`／`splits`；實際 native 僅 37 KB，體積重點是 5.5 MB 單一 dex。建議評估 R8 full mode 與 resource shrink 的邊界，而非 ABI 拆分。
- **L-26** 工作區 709 MB 無清理策略（`build.nosync` 417 MB、`captures` 98 MB、`docs` 95 MB、`dist` 28 MB）。建議加 `scripts/clean.sh` 與文件化的產物生命周期。
