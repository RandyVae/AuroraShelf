# Netgrey 游戏与双端产品完整审计报告

审计日期：2026-11-08  
审计对象：Netgrey Android & iOS 2.16.0-dev 及其集成游戏  
交接对象：Antigravity  
证据范围：Android/Kotlin 容器、iOS/SwiftUI 容器、共享 Web 游戏资源、数据配置、已有测试与构建记录。

## 1. 审计结论

项目已经形成一个可离线运行的游戏模块，包含大厅、剧情、编队、战斗、结果、养成、抽卡、商店、设置与 Slot。Android 与 iOS 通过 WebView 加载同一套游戏资源，并提供退出、静音、震动等原生桥接。功能骨架完整，视觉和数值系统也已有明显投入。

当前不具备“全量验收通过”的证据。缺少同一版本在 Android 手机、Android 平板、iPhone、iPad 上的运行截图和逐流程操作记录，无法确认所有 UI、动画、方向、动态字体、无障碍和退出恢复状态。现有测试主要覆盖 Kotlin 数据层和部分游戏逻辑，尚未覆盖完整 Web UI、真实设备手势、Canvas/Spine 渲染和长时间运行。

正式交付前优先处理 P0/P1 项，并建立四端截图基线。

## 3. 双端与 iPad 审计

### 3.1 Android

- `GameActivity` 使用 WebView 加载本地游戏资源，保留沉浸式窗口、保持屏幕常亮、透明系统栏和原生退出胶囊。
- 使用 `GameNativeBridge` 提供震动，游戏脚本通过 `AndroidNative` 触发原生反馈。
- WebView 使用 `textZoom=100`，游戏 Activity 固定竖屏。平板横屏、系统字体放大和折叠设备状态没有本轮运行证据。
- WebView 控制台消息当前被直接消费，线上诊断信息不足。
- 页面级退出和返回路径存在，但快速退出战斗、自动 Slot、CG 和特效时的定时器与动画帧统一清理没有证据。

**判定：P1 未完成设备适配验收，P2 诊断与生命周期风险。**

### 3.2 iPhone

- `GameContainerView` 使用 `WKWebView`，注入 `NativeBridge`，提供退出、震动、提示和静音绑定。
- 原生层使用毛玻璃浮动控制胶囊，方向和安全区由 SwiftUI 外层处理。
- 游戏内部主要由共享 Web CSS 决定布局，因此 iPhone 的小屏断点、刘海安全区、长文本和动态字体必须通过运行截图确认。
- 当前没有本轮 iPhone 游戏大厅、战斗、Slot、结果和退出恢复的完整证据。

**判定：P1 流程可用性与视觉验收未关闭。**

### 3.3 iPad

- iPad 复用 iPhone 的游戏 WebView 和共享游戏布局，项目主界面已有 iPad 自适应设计，但游戏内部没有独立的 iPad 信息架构证据。
- Slot 的 5×3 盘面、支付表、角色立绘和结果浮层在宽屏上可能出现过度留白或横向放大不足。
- 战斗三路单位、战斗 HUD、战斗日志、胜利/失败浮层需要检查横屏和竖屏两种状态。
- 不能用主 App 已通过的 iPad 适配记录替代游戏页面的验证。

**判定：P1，iPad 游戏布局和方向未验证。**

## 4. 所有界面 UI 元素设计

### 4.1 页面与导航

已发现页面状态包括 `boot`、`title`、`hub`、`campaign`、`story`、`battle`、`result`、`squad`、`gacha`、`roster`、`shop`、`slots`、`settings`。导航由共享 Web App controller 控制，主要入口来自大厅和底部导航。

### 4.2 已有 UI 资产与组件

- 开场与剧情：标题、故事文本、剧情过场、章节和阶段入口。
- 战斗：顶部 HUD、速度按钮、跳过按钮、三路战斗区域、角色标签、血条、伤害数字、技能、连击、战斗日志、胜利和失败浮层。
- Slot：标题栏、Jackpot rail、机械机柜、5×3 转轴、支付线、中奖线覆盖层、中奖金额、投注控制、主旋转按钮、金币盘、支付表、角色提示、奖励立绘和 CG 叠加层。
- 养成：编队槽位、角色卡、装备槽位、商店、抽卡、任务和设置。
- 原生承载：Android 退出胶囊，iOS 毛玻璃控制胶囊和 NativeBridge。

### 4.3 UI 设计问题

| 严重度 | 问题 | 影响 |
| --- | --- | --- |
| P1 | 游戏内部 UI 仍是 Web/CSS 体系，原生 App 容器与游戏内视觉语言之间缺少统一 token 和明确层级 | 容易呈现“嵌入网页游戏”的割裂感 |
| P1 | 战斗 HUD、角色、伤害数字、连击和技能特效同时叠加 | 小屏可读性和信息优先级存在风险 |
| P1 | 结果、复活、体力恢复、Slot 救济和充值弹窗可能连续出现 | 关键动作被遮挡，恢复路径不明确 |
| P2 | Canvas 内容缺少可验证的系统语义 | TalkBack、VoiceOver、键盘和辅助技术支持不足 |
| P2 | Slot 支付表和奖励文案在小屏下有单列降级，但未有动态字体和长文本证据 | 本地化与字体放大可能溢出 |
| P2 | 视觉减少动态效果已有 CSS 分支，但没有完整运行验收 | 无法确认 Canvas、视频、音频和震动同步降级 |
| P3 | CSS 末端存在历史空行和其他工作树格式噪音 | 降低审计信噪比，不影响运行 |

## 5. 使用功能审计

### 已接入功能

- 离线游戏数据加载和本地存档。
- 剧情章节、阶段选择、体力消耗和扫荡。
- 三路队伍编成、英雄与敌人单位、技能和装备。
- 战斗速度、跳过、战斗日志、连击、技能和结果结算。
- 抽卡、角色名册、商店、任务和设置。
- Slot 下注、旋转、自动旋转、免费旋转、中奖线、奖金统计、角色奖励、CG 和救济。
- Android/iOS 原生退出、静音、震动和 WebView 承载。

### 功能风险

1. 战斗退出、跳过、自动运行、复活和结果结算的重复点击幂等性未被完整测试。
2. Slot 自动旋转、页面切换、背景切换和系统中断时的状态恢复未被完整测试。
3. 游戏路由依赖 DOM 元素和全局对象，单页刷新或资源加载失败时的错误状态需要确认。
4. 网络不是游戏核心依赖，但首次资源加载失败、资源损坏和部分 JSON 缺失的界面状态未形成验收清单。
5. Android 与 iOS 共享 JS，有利于一致性，但原生桥接差异会造成震动、退出和系统返回行为差异。

## 6. 游戏数值与规划

### 6.1 战役数值

- 新手阶段 1-1 至 1-3 使用攻击、暴击和指挥官能量加成，开局能量为 65。
- 普通阶段开局能量为 25，战斗时间通常为 60 秒，新手阶段可使用更长计时。
- 角色攻击、生命、暴击和减伤通过 `Balance` 与成长数据计算。
- 章节、敌人、技能、装备、任务和扫荡形成了基本的长期成长结构。

### 6.2 Slot 数值

- 5 reels × 3 rows，9 paylines，下注范围 10 至 200，默认下注 20。
- 8 类符号，包含英雄、敌人、Wild 和 Scatter。
- Scatter 达到 3 个触发 5 次免费旋转。
- 前五转存在脚本化甜头，后续存在 Near-Miss，破产后有救济和额外奖励路径。

### 6.3 数值问题

| 严重度 | 问题 | 影响 |
| --- | --- | --- |
| P1 | 早期转数、救济、免费旋转和 Near-Miss 直接改写盘面 | 胜率、RTP、方差和玩家预期无法从配置直接推导 |
| P1 | 战役加成、复活、充值恢复和首胜奖励叠加关系没有单一平衡表 | 容易导致前期秒杀、后期断层或付费恢复过强 |
| P1 | 没有可审计的 RTP、命中率、平均奖励、破产率和章节通关曲线 | 无法判断数值是否支持长期留存和可控经济 |
| P2 | Slot 符号权重和支付表存在，但缺少 1 万、10 万和不同下注档的统计报告 | 不能仅凭单次结果判断经济平衡 |
| P2 | 虚拟币与充值文案同时存在，产品边界和付费计划需要明确 | 运营、合规和体验叙事可能不一致 |

### 6.4 规划建议交接

Antigravity 应先建立一份可计算的平衡表，至少包含每阶段敌我 DPS、有效生命、技能循环、体力消耗、奖励、失败恢复、Slot RTP、Scatter 触发率、免费旋转平均收益、Near-Miss 频率和破产救济上限。所有脚本化体验应有配置开关和统计记录，避免把体验剧本隐藏在结果生成函数中。

## 7. 战斗特效与战斗过程

### 已有表现

- Spine 角色渲染与资产预加载。
- 角色阴影、单位标签、投射物、受击、伤害数字、死亡消散、连击提示和技能特效。
- Squash & Stretch、受击反馈、濒危红光、天基爆闪和 EMP 级别的全屏反馈已在代码中出现。
- 战斗背景按章节切换，支持技能、自动战斗、速度和跳过。

### 战斗过程审计

1. 开场阶段需要验证背景、角色入场、HUD 和首个可操作状态是否在同一时间轴上稳定出现。
2. 目标选择、攻击前摇、命中、受击、伤害数字、死亡和连击应保持因果顺序，避免动画先于逻辑或多个特效覆盖同一单位。
3. 低血量警报、技能爆闪和大数字需要控制频率，否则会削弱重要事件层级。
4. 战斗速度切换和跳过必须保证结算只执行一次，且不遗留投射物、音频、定时器和 CSS 状态。
5. 胜利、失败、复活、失败重试和返回章节必须在低端设备和中断后恢复正确。

**判定：表现系统已具备较强基础，端到端视觉和性能证据不足，列为 P1 未验收。**

## 8. Slot 游戏设计元素排列

### 当前排列结构

- 顶部为标题与 Jackpot 信息。
- 中部为机械机柜和 5×3 转轴。
- 转轴周围有中奖线覆盖、中奖提示和状态消息。
- 下方为下注、自动旋转、主旋转和金币盘。
- 更下方为支付表、角色提示和奖励说明。
- 大奖或角色命中时显示全屏奖励立绘或 CG。

### 排列问题

| 严重度 | 问题 | 影响 |
| --- | --- | --- |
| P1 | 盘面、中奖线、状态消息和奖励提示同时竞争注意力 | 用户难以快速确认中奖来源和最终金额 |
| P1 | 5×3 盘面在小屏和 iPad 宽屏采用同一核心结构 | 小屏可能拥挤，宽屏可能出现空洞和比例失衡 |
| P2 | Jackpot、余额、下注、上次中奖和免费旋转信息需要明确主次 | 核心动作和状态反馈不够集中 |
| P2 | 奖励立绘与 CG 叠加层可能打断连续旋转流程 | 自动旋转和返回路径需要明确 |
| P2 | 需要验证 Scatter、Wild、中奖线和 Near-Miss 的色彩语义在深浅色与色觉差异下是否可区分 | 可能误读结果 |
| P3 | 机械机柜视觉与主 App 的原生玻璃导航语言存在风格距离 | 一体化体验不足 |

### 推荐排列基线

1. 顶部只保留余额、当前下注和免费旋转状态。
2. 盘面保持唯一视觉焦点，中奖线只在结果确认阶段出现。
3. 主旋转按钮固定在安全区内，自动旋转和下注作为次级动作。
4. 支付表和符号说明使用可折叠面板，避免压缩盘面高度。
5. 大奖表现采用单一奖励层，完成后明确返回盘面或继续自动旋转。

## 9. 优先级与交接任务

### P0

- 建立 Android 手机、Android 平板、iPhone、iPad 的四端运行基线。
- 修复或验证战斗与 Slot 的退出、重进、自动运行中断、结果幂等和存档恢复。

### P1

- 重做游戏内 UI 层级和小屏/宽屏断点。
- 建立战斗逐帧验收，包括入场、攻击、命中、死亡、技能、连击、胜利和失败。
- 建立 Slot 逐步验收，包括待机、旋转、停轮、中奖、Scatter、免费旋转、大奖、自动旋转、破产和恢复。
- 生成数值模拟报告，明确 RTP、奖励分布、通关曲线和恢复上限。
- 补充 TalkBack、VoiceOver、动态字体、减少动态效果、深浅色和方向验证。

### P2

- 统一游戏与主 App 的颜色、字体、玻璃材质、按钮状态和安全区规则。
- 建立截图基线与视觉回归清单。
- 保留可控调试日志，不再吞掉 WebView 控制台错误。
- 优化特效、音频、视频和定时器的生命周期清理。
