# Lust Goddess 单机战术版审计报告

审计日期：2026-10-29（Asia/Hong_Kong）  
审计对象：`offline/` 当前 Web 版、`android/` Android 外壳与 `dist/LustGoddess-1.2.apk` 交付物。  
审计方式：当前源码阅读、当前本地运行、1365×900 与 390×844 截图、CDP/浏览器流程、静态检查、Android 构建，以及主流卡牌游戏公开资料对比。

## 结论先行

当前项目已经超过“许愿式原型”：它是一个能启动、能保存、能完成战役和战斗、包含抽卡/养成/图鉴/音频/剧情的单机战术 RPG 垂直切片。当前 Web 流程的自动化验证也比较完整：剧情与战斗串联 10/10、综合审计 8/8、扩展系统 9/9、角色尺寸与 CG 播放验证通过。

它还没有达到“主流卡牌游戏完成度”或“可直接发布”的标准，原因集中在四处：

1. **手机布局是发布阻塞项。** 390×844 时页面实际宽度为 496px，导航、战斗按钮、章节卡和大部分页面被横向裁切。
2. **养成详情存在真实布局缺陷。** `#hero-detail-empty` 带有 `hidden`，但 CSS 仍让它 `display:grid`，它占满面板高度，把角色详情推到约 3081px 之后；桌面首屏因此看见空白详情面板，手机上几乎找不到详情。
3. **它目前是“英雄队伍回合制 RPG”，不是完整的卡牌游戏。** 代码和数据没有牌组、手牌、抽牌、能量/费用、弃牌堆、卡牌构筑或卡牌奖励循环；“卡牌”主要出现在抽卡展示和 UI card 样式名里。
4. **默认存档是测试员模式。** 启动时无条件解锁 21 名角色、99,999,999 金币、99,999 契约、全部章节和试炼，导致经济、解锁、留存和难度无法按真实玩家路径验收。

综合判断：**功能完成度约 6/10，桌面视觉约 6/10，移动可用性约 3/10，卡牌核心约 2/10，发布准备度约 3/10。** 先修布局、对比度和测试/正式存档边界，再决定是否把项目发展成真正的卡牌构筑游戏。

- **完整可玩路径已经存在。** 标题 → 章节 → 战前剧情 → 3v3 战斗 → 三星结算 → 奖励写入，当前运行可完成。

## P0/P1 风险：先处理这些

### P0：移动端内容被裁切

在 390×844 当前运行测得：`document.documentElement.scrollWidth = 496.1875`，大于 viewport 390；顶部栏宽 496px，物资区宽 419px，导航位于 x=443px，绝大部分导航落在屏幕外。战斗操作区宽 472px，技能按钮右边界约 484px，用户看不到完整按钮。

这不是“需要再精致一点”，而是核心操作不可见。当前 `.topbar` 依赖 flex 换行，但 `.stats` 仍有较大的最小宽度；`.battlefield` 和行动按钮也按桌面宽度计算。章节、队伍、补给、图鉴的移动截图都出现同类裁切。

**建议修复顺序：**

1. 顶部栏改成移动专用结构：品牌 + 物资摘要 + 菜单按钮，导航放入可关闭的原生 drawer/sheet；不要让 8 个 tab 和物资同时争夺一行。
2. 所有移动断点显式使用 `min-width: 0; width: 100%; max-width: 100%`，禁止页面根宽度超过 viewport；用 `overflow-x: clip` 作为保护而不是掩盖布局错误。
3. 战斗在窄屏改成敌方两列/单列、我方单列或横向可聚焦列表，底部行动按钮每行一个，保证攻击、技能、自动、撤退都可见。
4. 用 320、360、375、390、430px 和文字 200% 做截图回归，任何水平滚动都作为失败。

### P0：角色详情被 `hidden` 元素撑开

当前运行中 `#hero-detail-empty.hidden === true`，但计算样式仍是 `display: grid`，高度 1373px；`#hero-detail-content` 从 y≈3081px 才开始。原因是 `.hero-detail-empty { display:grid }` 和 `.hero-detail-content { display:grid }` 覆盖了浏览器对 `hidden` 的默认隐藏行为，样式表只给 `.view[hidden]` 和 `.result[hidden]` 写了强制隐藏。

**建议：** 在全局加入 `*[hidden] { display: none !important; }`，或至少为这两个组件和所有动效层加入显式 `[hidden]` 规则；修复后重新截取桌面、移动和键盘焦点证据。

### P1：深色游戏面板上的文字对比度不足

当前系统处于浅色主题时，`--text` 被设成深色 `#0f141f`，但标题页、招募横幅、剧情对白和战斗背景仍是深色图片/深色遮罩。当前截图中标题 “Lust Goddess”、招募标题、剧情对白和战斗日志都接近不可读。战斗截图还显示通讯浮层、目标卡和操作区文字被背景吞掉。

**建议：** 给深色媒体表面建立独立 token（例如 `--on-media: #fff`、`--on-media-muted: rgba(255,255,255,.78)`），不要直接继承浅色页面的 `--text`；用实际截图做 WCAG 对比度检查，正文至少 4.5:1，按钮文字至少 3:1。

### P1：当前核心玩法没有形成卡牌循环

`offline/game_data.json` 的顶层数据是 heroes/enemies/chapters/trials/equipments/shop_items/daily_quests/elements/achievements，没有 deck/cards/hand/draw/discard/mana/energy 等结构；`offline/app.js` 的战斗行动只有普攻和特技，技能统一以固定冷却推进。抽卡得到的是英雄或碎片，而不是战斗中会抽取和打出的牌。

因此产品定位应二选一：

- **如果目标是战术 RPG：** 去掉“卡牌 RPG”表述，把英雄、装备、战斗技能做深，减少玩家对牌组构筑的预期。
- **如果目标是卡牌游戏：** 增加真实的牌组/手牌循环，不要继续只加角色、CG 和资源系统。

推荐第二条，保留现有 3 人小队作为队长/阵营层，在战斗中增加一套可构筑的“战术牌”。

### P1：默认测试模式无法证明真实产品闭环

`defaultSave()` 和 `boot()` 都会无条件设置：全角色解锁、无限资源、全章节、全试炼、999 碎片。这样可以快速演示内容，但无法验证新玩家引导、首抽、资源稀缺、章节解锁、失败成本、升级曲线、每日任务或长期留存。

**建议：** 把 `qaMode` 作为显式构建开关或本地开发 query 参数；正式默认存档从 0 金币、起始队伍、第一章和有限抽卡资源开始。GM 控制台只在 QA 构建出现，生产构建不带入口。

## UX 与可访问性风险

- **导航发现性：** 移动端导航实际跑到屏幕右侧，用户只能依赖首页按钮；页面没有可见菜单入口。
- **语义：** 品牌使用 `div role="button" tabindex="0"`，但代码没有对应的 Enter/Space 激活处理；建议改成真正的 `<button>`。
- **战斗目标：** 敌方卡片在 AX 树中是普通 container，不是 button/radio；装备槽位也是可点击 `div`。屏幕阅读器用户无法稳定知道目标可选、当前选中项和激活方式。
- **焦点与模态：** 抽卡、装备、结果和图鉴灯箱的视觉状态存在，但需要逐项验证焦点移入、焦点留在模态内、关闭后回到触发按钮。
- **动效：** `prefers-reduced-motion` 和设置里的减少动效已经存在，这是优点；但要实测特写、震屏、自动播放和视频是否都真正降级。
- **音频：** 浏览器控制台记录了 AudioContext autoplay warning；应在首次用户点击后初始化音频并清掉启动警告。
- **错误噪声：** `/favicon.ico` 当前返回 404；这是小问题，但会污染 QA 控制台，应该补齐或显式处理。
- **截图证据不能替代完整无障碍验收。** 还需要键盘、TalkBack/VoiceOver、200% 文字、对比度和焦点顺序实测。

## 内容、数值与系统深度

当前系统数量不少，但深度仍偏薄：

- 21 名角色分为 SSR/SR/R，存在元素和职业差异；然而大量技能没有独立 cooldown 数据，代码对没有 cooldown 的技能统一使用 3 回合，差异主要落在倍率和效果类型。
- 8 章和 10 层试炼主要是固定敌人列表，没有分支路线、事件、随机奖励、关卡 modifier 或基于玩家选择的路线风险。
- 3 星条件目前是通关、回合数和全员存活，尚未形成多种真正不同的战术目标。
- 自动战斗和扫荡在测试模式下很方便，但如果没有敌方意图、资源决策、牌序或位置取舍，玩家手动操作的价值很低。
- “亲密度、图鉴共鸣、挂机、任务、成就、商城、抽卡、装备”都已出现，但它们共享同一套无限资源，尚未形成可验证的资源张力。

## 与主流卡牌游戏的对比

对比重点不是复制美术，而是看它们如何让“每一局”产生选择、构筑和复玩价值。

| 参照 | 主循环特点 | 当前项目差距 | 应借鉴的具体机制 |
|---|---|---|---|
| [Slay the Spire](https://store.steampowered.com/app/646570/Slay_the_Spire/) | 牌组随局构筑、路线每局变化、遗物产生组合；官方页面列出 350+ cards、200+ items、事件和多种遭遇 | 当前是固定章节列表，战斗不抽牌，没有路线、遗物、事件或牌组稀释 | 地图路线 + 战后多选一牌奖 + 移除/升级牌 + 遗物组合；先做小规模 30~50 张牌即可 |
| [Hearthstone](https://hearthstone.blizzard.com/en-us/) | 费用、法术、随从、关键词、预组、休闲/排名和跨设备进度；官方强调“易上手、长期有深度” | 当前没有费用曲线、手牌、卡牌关键词、对手玩家或预组导入 | 为每名队长设计费用曲线和关键词；提供 3 套预组，让新玩家能先玩再学构筑 |

| [Balatro](https://store.steampowered.com/app/2379780/Balatro/) | Joker、Deck、Tarot、Planet、Spectral、Voucher 多层组合；有 8 个难度、挑战和 seeded run，官方还提供统计页 | 当前养成是线性升等级/升星/装备，组合空间和 run 变化都很少 | 给牌组一个“构筑引擎”：牌、装备、遗物/指令三层相互改变；加入 seeded run、挑战规则和统计页 |
| [OpenDuelyst](https://github.com/open-duelyst/duelyst) | 卡牌与战术棋盘混合，开源仓库保留本地可运行路径、服务端和测试/贡献文档 | 当前虽有战术队伍，但没有棋盘位置、召唤/移动、卡牌和本地服务边界说明 | 如果坚持战术方向，借鉴“卡牌效果 + 位置”的统一规则层，并把本地运行、版本、数据迁移写成一等文档 |

开源实现也给出两个可落地的工程参考：[`xajik/thedeck`](https://github.com/xajik/thedeck)（767 stars，MIT，Flutter；将游戏、状态、use case 和持久化分层）适合参考移动端状态边界；[`open-duelyst/duelyst`](https://github.com/open-duelyst/duelyst)（3,938 stars，CC0）适合参考“战术卡牌 + 本地可运行”的交付结构。它们的许可证和代码结构需要在真正复用前单独核对。

## 推荐实施路线

### 阶段 0：发布阻塞修复

1. 修复全局 `hidden` 规则，确认养成详情首屏可见。
2. 重做移动端 shell 和战斗响应式布局，目标是 320~430px 无横向溢出。
3. 为深色媒体面板建立浅色文字 token，做对比度截图回归。
4. 把品牌、敌方目标、装备槽位和抽卡结果改成语义按钮/列表项，补焦点、键盘和屏幕阅读器状态。
5. 修复 favicon、AudioContext 初始化、硬编码 CDP target 和缺失的测试依赖说明。

### 阶段 1：确定卡牌核心

建议做一个可控的“战术牌”最小版本，而不是一次性复制大型 CCG：

- 3 名英雄仍保留；每名英雄带 8~12 张个人牌，队伍组成 24~30 张牌组。
- 每回合抽 5 张牌，能量从 3 增至 6；牌有攻击、防御、位移、状态、召唤和抽牌效果。
- 加入弃牌堆、消耗牌、牌组查看、牌的升级/移除和战斗日志。
- 战斗增加敌方意图、结束回合、位置/三战场区和至少 6 个清晰关键词。
- 每章战后给 3 选 1 牌奖励，试炼提供 modifier；这样才有“我这局为什么这样构筑”的复玩理由。

### 阶段 2：恢复真正的成长曲线

- 正式新存档与 QA 存档分离。
- 先做一条 20~30 分钟的新手路径，验证首抽、首个升级、第一次失败、第一次扫荡和第一张稀有牌。
- 让金币、契约、碎片、装备和牌组升级各自有用途与取舍；无限资源只用于 QA。
- 为每章和每个试炼写清楚解锁条件、奖励、三星条件、失败成本和推荐战力。

### 阶段 3：内容与发行门槛

- 8 章加入分支事件、随机节点、不同敌方意图和至少 3 种 Boss 机制。
- 把 21 名角色从“不同数值 + 一个技能”升级成可识别的构筑轴，例如毒伤、护盾转伤、弃牌、召唤、位置移动、低血反击。
- 完成正式签名、设备矩阵（Android 14/15/16，低端机、平板、折叠屏）、性能/内存/视频耗电检查。
- 补齐隐私政策、年龄门槛、成人内容分级、素材权利和发布渠道所需的记录；18+ badge 不是年龄验证。
