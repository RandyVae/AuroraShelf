# 案例对照首分钟体验审计

日期：2026-10-29  
审计对象：`web/` 本地单机版（当前工作树）  
对照案例：`https://www.lust-goddess.com/play?...`  
审计重点：第一印象、首屏演出、角色尺寸、剧情上下文、镜头/转场、音频/反馈、战斗登场，以及美术/动画/VFX 是否达到可交付标准。

## 结论

**当前版本仍未达到成品首分钟标准。** 资源数量和技术校验已经达到 Vertical Slice 可玩基础：55/55 英雄、168/168 敌人资源校验通过，7 状态 manifest、VFX 模块和 Android APK 都已落盘。但用户指出的问题仍然存在：进入第一关后是“静态背景 + 单角色立绘 + 对话框”，随后用一个约 1.5 秒的队长 Spine 特写直接切入自动战斗；这不是一个完整的序章演出，也不能替代完整动态主角色、镜头和事件链。

当前首分钟评级：**条件通过（Vertical Slice）/ 成品候选不通过**。

- P0：首分钟缺少连续的主线演出，第一印象仍像测试场景。
- P1：战斗登场特写只有队长单人，时长短、无事件分镜、无敌我对切、无战前目标确认。
- P1：动画 manifest 的 `enter`、`skill`、`fall`、`victory` 多数是代码/VFX 合成回退，不是对应的原生 Spine 动画；静态校验通过不能等同于视觉验收。
- P1：案例协议之后的完整剧情/战斗流程本轮没有完成验证，因为页面进入协议弹窗，代替用户接受第三方协议需要用户明确授权。
- P2：声音、语音、转场节奏和失败/跳过/自动播放的完整组合尚未形成逐事件验收证据。

## 证据边界

### 案例网站实测

浏览器实测入口为用户提供的 Lust Goddess URL，使用 ChatGPT in-app browser，视口约 435×664。

1. 首次进入先显示年龄验证：全屏背景、锁图标、年龄说明、绿色“立即进入/我已年满18岁”按钮，以及服务条款和隐私政策链接。
2. 点击年龄确认后，出现加载/主视觉页面：顶部为多角色主视觉图，页面有明显的版本号、绿色“游戏”按钮、加载进度和设置/全屏控制；背景场景与主视觉形成明确层级。
3. 继续加载后出现“用户许可协议”弹窗。审计在此停止，没有替用户点击“接受”，所以协议后的剧情、战斗和音频不被列为已验证事实。

案例可确认的设计信号是：**进入前置流程有明确状态、主视觉由多角色组成且占据首屏核心区域、场景背景和主视觉有层级、加载/协议/按钮状态可见**。这些信号本身已经比“进入后一个小人物持续晃动”更完整，但不代表案例的协议后玩法已在本轮验收。

### 当前本地版本实测

本地服务：`python3 web/serve.py`，`http://127.0.0.1:8100/index.html`。实测顺序：标题 → 大厅 → 第一章 → 第一关 → 战前剧情 → 跳过剧情 → 战斗登场。

1. 标题页有城市背景、LUST GODDESS 标题和“开始游戏”，首屏结构清楚，但没有动态主角色或序章事件。
2. 大厅显示资源、战役、招募、编队、图鉴和商店入口；主角区只提供一条状态文案。
3. 第一章第一关进入前展示 `chapter.story` 的 4 句对白。实测可见 Kitty 的 `lega.webp` 大立绘，背景为 `assets/bg/ch1.webp`，对白框和自动播放/跳过控件正常出现。
4. 跳过剧情后立即进入战斗。`runBattle()` 在 `#battle-entrance-cutin` 显示队长 Kitty、队长口号和全屏速度线/暗色遮罩；随后约 1500ms 隐藏特写并恢复自动战斗。
5. 实测截图中队长特写确实比普通战斗单位大，但它仍是单角色、单口号、单镜头、单时长事件，没有角色入场顺序、敌方响应、战术目标、镜头推进、对白承接或战前音频事件。
6. 战斗主画面随后回到固定战场和三名单位卡片，主要动态来自 Spine idle、代码位移和轻量 VFX。它可玩，但视觉叙事没有继续推进。

## 代码与资源核验

- `web/js/app.js:89-160`：剧情只是按数组逐句打字，切换单张 `story-art`；没有镜头轨道、角色入场轨道、事件/音频轨道。
- `web/js/app.js:228-322`：战斗启动后先 `b.start()`，再显示 `#battle-entrance-cutin`，固定 `setTimeout(..., 1500)` 隐藏；这证明它是战斗覆盖层，不是首屏序章。
- `web/index.html:113-131`：剧情 DOM 只有背景、单张 `<img>`、对白框和两个控制按钮。
- `web/index.html:145-158`：登场 DOM 只有一个 Spine canvas、一个队长名字、一个口号和速度线背景。
- `web/data/animation-manifest.json`：`enter`、`skill`、`fall`、`victory` 明确使用 `native: null` 或代码回退；文件自身已经承认这部分不是原生动作覆盖。
- `web/js/vfx.js`：提供 slash、projectile、hit spark、skill flash、heal、shield、freeze、camera punch、victory burst；这些是轻量特效层，不能替代剧情分镜、角色表演或完整技能演出。
- `tools/verify_curated_assets.py`：55/55 英雄、168/168 敌人和音频映射校验退出码 0。该结果只证明文件和映射完整，不证明首分钟视觉质量。
- `web/assets` 约 158 MB；已存在角色大图、背景、CG 视频和 Spine 资源，但首分钟流程只调用了其中一小部分。

## 给 Antigravity 的整改工作包

### P0：重做首分钟序章

把第一关首次进入改成一条可观察的事件链，最低要求：

1. 2.5–5 秒全屏主角色登场：至少 1 名主角的大尺寸动态立绘/Spine，角色占战斗视口高度约 65% 以上。
2. 至少 3 个可见事件：环境建立 → 主角入场/动作 → 敌方或任务目标响应 → 进入战斗。
3. 至少 2 名角色参与镜头或对白，不能只有队长名字和一条口号。
4. 角色、对白、背景、镜头推进、音频/SFX、转场必须由同一条序章 timeline 驱动；禁止只在 `runBattle()` 外包一个 1.5 秒 overlay。
5. 提供跳过和自动播放，但跳过必须保留状态初始化，自动播放必须等待事件完成，不得用固定短 timeout 造成截断。

### P1：建立演出数据契约

新增机器可读的 `intro-sequences.json` 或等价数据结构，至少描述 `background`、`actors`、`camera`、`dialogue`、`audio`、`vfx`、`duration`、`skipTo`。每个首次关卡应有可追踪事件 ID，运行时日志记录事件开始/完成。

### P1：补齐动态资源验收

优先为 Kitty、Dominica、Regina 三名代表角色补真实 `enter/attack/skill/hit/fall/victory` 动作或可验收的替代演出；截图/录屏需证明角色动作不是只靠缩放、位移、透明度。其余角色继续使用 manifest 回退，但必须在报告中按“原生/合成”分开统计。

### P1：战斗前后连续性

战前序章结束时保留任务目标或战术无线电提示；战斗胜利后接至少一个 2–3 秒的余波/胜利镜头，再进入结算。战斗场景、角色立绘和 CG 视频资源要建立明确的调用关系。

### P2：验收证据

Antigravity 交付下列证据后再宣称完成：

- 桌面端 0s、1s、3s、5s、战斗开始、战斗结束截图；
- Android APK 同一流程截图或录屏；
- 首分钟事件日志，包含序章事件 ID 和完成时长；
- 关闭/开启 Reduce Motion 各一套证据；
- 资源 manifest、原生动作/合成动作清单和授权来源；
- 不把 `verify_curated_assets.py` 或 E2E PASS 单独当成视觉验收。

## 复核门槛

在满足以下条件前，状态保持“Vertical Slice / 不通过成品首分钟验收”：

- 首次进入第一关能看到连续序章，而不是单个 1.5 秒队长覆盖层；
- 主角色在首分钟有大尺寸、可辨识、可解释的动态表演；
- 剧情、镜头、音效、VFX、战斗和结算形成连续事件链；
- 桌面和 Android 都有对应截图/录屏；
- 原作素材公开分发授权得到书面证明，或切换为已授权/原创资源。
