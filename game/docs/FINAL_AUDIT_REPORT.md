# Lust Goddess Local Edition 成品化审计报告

**审计日期：** 2026-10-29  
**审计对象：** `/Users/itou/Documents/project-hgame/web`、`android/`、`dist/` 及其数据和资源生成链  
**审计目标：** 判断当前项目距离“可交付的完整游戏”还缺什么，并给出后续 AI 可直接执行的建设顺序。  
**结论等级：** 可玩原型 / Vertical Slice，尚未达到商业成品、正式上架或原版 1:1 复刻标准。

## 1. 管理层结论

这个项目已经超过单纯 UI 框架：它有本地资源、完整主流程、55 名单位、8 章 41 关、招募、编队、图鉴、商店、剧情、Spine 渲染、音频、回合制战斗和 Android 外壳。现有版本可以被称为“可玩的本地版原型”。

但它距离成品仍有三条关键断层：

1. **产品闭环不完整。** 当前核心循环是“选队 → 看剧情 → 自动战斗 → 领奖”，角色成长和长期目标很薄，养成、装备、任务、活动、挑战、失败恢复、内容解锁没有形成可持续的玩家目标。
2. **战斗实现不是原作逻辑，也不是完整战术系统。** 当前为三路自动战斗，技能按 token 语义近似执行；没有可验证的原版公式、完整敌方 AI、可控的战术决策层和战斗回放。
3. **发布条件未满足。** APK 是 debug 签名；没有 API 36 真机、平板/折叠屏、TalkBack、200% 字体、性能、崩溃恢复、隐私/年龄验证和素材授权的完整证据。原 Unity 客户端离线重放仍卡在 `LoadAllStaticContentInfo / LoadedAssets=0`，不能把本地重制版宣称为原版 1:1。

**建议产品决策：** 将“单机原创化重制版”作为主交付路线，把“原版 Unity 1:1 离线化”保留为独立研究支线。继续投入 1:1 之前，必须先明确版权、商业授权和可接受的复刻边界；否则会长期被客户端静态资源加载和服务端协议阻塞。

## 4. 关键技术发现

### 4.1 当前架构优点

- 纯静态 Web 资源，迭代快，运行时依赖少。
- `web/js/app.js` 已能串起启动、路由、剧情、战斗、招募、商店、设置。
- 战斗、平衡、存档、UI、Spine、音频已有分文件边界，适合继续拆分。
- Android 使用固定 loopback origin，能够保持 WebView 存储；AssetServer 支持 Range，适合视频/音频流式读取。
- 资源提取、数据生成、E2E 工具已经存在，具备建立可重复流水线的基础。

### 4.2 当前架构风险

1. **状态集中在全局对象。** `APP.state`、`APP.data`、`APP.battle` 和 DOM 事件共同承担业务状态，后续加养成、任务、活动时容易出现跨页面不同步和重复绑定。
2. **存档是客户端信任边界。** `localStorage`/`AndroidSave` 保存完整 JSON，用户可直接修改金币、抽卡、通关和设置；适合单机，不适合联网、公平排行或付费。
3. **数据契约没有版本化。** `save.js` 只做浅合并，未提供 schema version migration、字段范围校验、未知字段策略、重复/非法单位修复。
4. **战斗可重复性不足。** 使用 `Math.random()`，没有战斗种子、事件日志和重放格式，难以复盘玩家报告的数值问题。
5. **配置与实现不一致。** `constants.json` 的 `maxEnergy=3`，而新存档默认 `energy=60`；这会造成体力上限和恢复行为不一致，应在数据校验阶段阻断。
6. **单文件控制器偏大。** `app.js` 约 485 行，`battle.js` 约 484 行；目前尚能维护，但加系统时应按 domain 拆分，而不是继续堆叠回调。
7. **外链统计不严谨。** E2E 把 `data:` URI 当成 external；发布门槛必须区分 `http/https/ws/wss` 与内嵌资源。
8. **错误处理有吞错。** Android bridge 和存档写入部分 catch 后静默回退；需要把“桥不可用、配额不足、存档损坏”变成可诊断状态。

## 5. 目标产品逻辑框架

后续 AI 应按下列层次建设，不要直接在页面事件里继续添加规则：

```text
AppShell
├── Navigation / Screen lifecycle
├── Accessibility / Input / Audio focus
├── Session
│   ├── SaveRepository (Web + Android)
│   ├── SaveSchema + migrations + validation
│   └── Clock / offline-time policy
├── Game Domain
│   ├── PlayerProfile
│   ├── Roster / CharacterInstance
│   ├── Squad / Formation
│   ├── Progression (level, star, skill, equipment)
│   ├── Campaign / StageUnlock / Rewards
│   ├── Battle (rules, state machine, RNG seed, event log)
│   ├── Gacha / Pity / DuplicateConversion
│   ├── Economy / Shop / Missions / Achievements
│   └── ContentAccess / AgeGate / Entitlement
├── Data
│   ├── versioned JSON schemas
│   ├── generated content manifests
│   └── balance snapshots
└── Presentation
    ├── Hub / Campaign / Story / Battle / Result
    ├── Squad / Roster / Detail / Gacha / Shop / Missions
    └── Settings / Save management / Legal
```

所有领域系统应提供纯函数或小型 service：输入状态与命令，输出新状态和事件。UI 只订阅状态并渲染；不要让 UI 直接修改金币、体力或角色数组。

## 6. 推荐建设顺序

### Phase 0：冻结基线（1–2 天）

- 把当前版本复制为只读基线，生成 `BUILD_MANIFEST.json`（源码、数据、资源、APK 哈希、工具版本）。
- 修 E2E external URI 判定，固定 Chrome/Android 测试环境。
- 定义产品路线：单机重制版；原版 1:1 作为研究支线。
- 建 `data/schema/`、`docs/adr/`、`qa/` 和版本化存档格式。

**出口标准：** 任意 AI 能在干净目录启动 Web、构建 APK、运行一条可重复 E2E，并知道它验证的是哪一个版本。

### Phase 1：核心状态和存档（P0，3–5 天）

- 实现 `SaveSchema v2`：profile、roster instances、inventory、currencies、campaign、missions、settings、analytics opt-in。
- 增加迁移器 v1→v2、字段范围校验、非法单位过滤、原子写入、备份槽和损坏恢复。
- 修复体力配置；明确最大体力、恢复周期、离线时间回拨策略。
- 让所有经济变化通过 `EconomyService`，记录 reason、source、sink 和 transaction id。

**出口标准：** 伪造存档会被拒绝或修复；旧存档可升级；清空/损坏/进程中断不会丢失上一份有效存档。

### Phase 2：角色成长和经济闭环（P0，5–8 天）

- 角色从“静态 hero key”变为 `CharacterInstance`：等级、经验、星级、技能等级、碎片、装备。
- 添加角色详情、升级、突破、技能升级和装备三槽位。
- 建立金币、碎片、经验、装备材料的来源/消耗表，做 30 天经济模拟。
- 招募实现池版本、概率快照、保底计数、重复转化和结果日志；测试版无限资源必须通过构建时 feature flag 与正式版隔离。

**出口标准：** 新玩家可在 30–60 分钟内完成第一次成长；中期资源有明确瓶颈；不存在无限资源默认开关。

### Phase 3：战斗系统稳定化（P0，7–12 天）

- 先冻结规则文档：属性、伤害、克制、护盾、状态、触发顺序、死亡/复活、时间、胜负和三星。
- 将战斗改为 `BattleState + Command + Event` 状态机；所有随机由 seed RNG 提供。
- 明确当前产品方向：自动战斗或可操作战术战斗。若保留自动战斗，增加编队/队长/技能释放/目标策略等可理解决策；若做战术战斗，增加部署、行动点、玩家回合和撤销/暂停。
- 加入战斗 replay JSON、战斗快照和确定性测试。
- 敌方从“无技能或极少技能”升级为按 archetype 配置的 AI：前排、治疗、控制、Boss、召唤。

**出口标准：** 同 seed 同结果；1000 场模拟无 NaN/负血/死后行动/无限循环；关键战斗有录制和回放。

### Phase 4：内容和长期循环（P1，7–14 天）

- 新手引导、每日/周任务、成就、试炼/Boss、重复关卡扫荡。
- 章节解锁、奖励预览、失败原因、重试、跳过已看剧情、剧情回顾。
- 角色关系/好感或其他长期目标必须有数据定义和 UI 入口，不能只保留导航按钮。
- 活动配置使用开始/结束时间、版本、奖励表和回滚策略；单机版可先做本地活动日历。

**出口标准：** 玩家完成主线后仍有至少三种可解释的目标；所有入口都能到达真实功能或明确显示“即将开放”。

### Phase 5：质量、无障碍和发布（P0，5–10 天）

- Web：390×844、412×915、平板横屏、桌面宽屏；动态字体 100/150/200%；键盘、焦点、减少动效、对比度。
- Android：API 34/35/36、真实设备、平板/折叠屏、TalkBack、后台恢复、低内存、旋转策略、音频中断。
- 性能：首屏、战斗帧率、Spine 内存、视频首帧、APK 安装体积、AssetServer Range。
- 安全：导入存档大小/JSON 深度/字段白名单，路径遍历，WebView bridge 暴露面，release 混淆和签名。
- 合规：原素材/Spine runtime/音频/视频授权，18+ 年龄门槛、隐私政策、商店分级和截图。

**出口标准：** release signed APK、完整 QA 报告、隐私/年龄/授权文件齐全；任何 P0 失败都不得称为“成品”。

## 7. 不能混淆的两条路线

### 路线 A：单机重制版（推荐）

以 `web/` + `android/` 为产品源，使用已获授权或原创资源，允许自定义战斗公式和剧情。目标是“独立可玩的完整游戏”，不宣称原版 1:1。需要完成上面的状态、成长、战斗、长期循环、发布和授权工作。

### 路线 B：原 Unity 1:1 离线化（研究支线

继续使用 `replica/`、暖机 profile、Unity WebGL build 和服务端快照。当前卡在 `LoadAllStaticContentInfo`、`LoadedAssets=0`，并且 23.0.1 配置/API 快照不完整。除非获得合法授权、完整服务端数据和客户端补丁，否则不能作为可交付成品路线。

## 8. P0 风险清单

- **版权/授权：** 当前文档明确提示原素材仅限本机研究；未获得授权前禁止商业发布。
- **成人内容：** 18+ 开关只是内容显示设置，不等于年龄验证、地区合规或平台合规。
- **经济作弊：** 本地存档可修改；不能用于联网排行、真实付费或公平竞争。
- **debug 签名：** 当前 APK 只适合侧载，不能上架。
- **配置错误：** `maxEnergy=3` 与默认 60 不一致，先修数据契约再扩充内容。
- **版本漂移：** 文档中同时存在 1.5、2.0、2.3 等历史产物；交付时必须以 manifest、源码和 APK 哈希三者绑定。
- **原版声明：** 当前战斗、剧情和数值均有重写/推断部分，不得写成“原版逻辑已恢复”。

## 9. 最终验收门槛

只有以下条件全部满足，才可把项目称为“成品候选版”：

1. 新玩家从首次启动到首次成长、首次招募、首次失败、首次三星和首次长期任务都能完成。
2. 存档 v2 可迁移、校验、备份、恢复；所有经济变化有可追踪原因。
3. 战斗规则文档与代码一致，固定 seed 可重放，关键边界有自动化测试。
4. 角色养成、装备、任务、挑战和商店形成可持续闭环。
5. Web 和 Android 的 P0 设备/无障碍/性能测试通过。
6. release APK 使用正式签名；资源、Spine、音频、视频和成人内容都有合法发布依据。
7. 发布说明明确写出“单机重制版”或“原版 1:1”，不混用两种身份。

**审计判定：** 当前为 **可玩原型（Playable Prototype / Vertical Slice）**；距离“商业成品候选版”至少还缺 Phase 1–5 的 P0 工作，预计是数周级持续开发，而不是补几张 UI 或增加几个关卡即可完成。

## 10. 完整开发建议：必须完成的内容

以下清单按“可以成为完整游戏”的最低产品范围编排。每一项都必须有数据、界面、运行逻辑、存档和测试，只有做出页面不能算完成。

### 10.1 产品和用户流程

- 首次启动：年龄/内容提示、语言、音频、画质、隐私说明、首次存档创建。
- 新手引导：大厅 → 编队 → 第一关 → 战斗操作/自动战斗 → 结算 → 第一次升级 → 第一次招募 → 第一个任务领奖。
- 主线流程：章节解锁、关卡预览、消耗确认、剧情、战斗、三星、掉落、下一关推荐、失败重试。
- 长期流程：角色收集、角色成长、装备、技能、任务、试炼、活动、图鉴、剧情回顾。
- 异常流程：资源不足、网络不存在、存档损坏、资源加载失败、进程被杀、返回键、音频中断、低内存。

### 10.2 角色和养成

- 角色实例 ID；同一角色的等级、经验、星级、技能等级、装备和好感独立保存。
- 角色等级和经验曲线；升级费用；等级上限和突破条件。
- 星级/突破：碎片数量、金币、材料、被动解锁、外观变化。
- 技能：主动/被动、等级、冷却、触发、目标、状态、描述和升级材料。
- 装备：武器、防具、核心槽位；品质、主属性、副属性、强化、锁定、分解、套装。
- 编队：队伍预设、位置、队长技、职业分布、种族/属性羁绊、推荐战力。
- 角色详情：属性解释、技能演示、语音、动画、故事、获得来源和未解锁状态。

### 10.3 战斗和关卡

- 把当前 `battle.js` 改成确定性的 `BattleState/BattleEngine/BattleRng/BattleReplay`。
- 明确实时自动战斗或半自动战术战斗的产品选择；不要长期停留在两种模式之间。

- 结算展示三星条件、战斗时间、存活人数、掉落预览、首次奖励、重复奖励和失败原因。
- 增加扫荡、快速战斗、战斗暂停、重试、战斗记录和 replay 导出。

### 10.4 经济和长期内容

### 10.5 运营、合规和发布

## 11. 动画系统完整建议

“有大量动画”必须建设成统一动画管线，而不是每个按钮单独写 CSS。动画分为角色动画、战斗表现、界面动效、镜头与特效四层。

### 11.1 角色动画清单

每个可用角色至少准备以下 Spine 状态；缺少原始动画时先制作低成本替代动作，接口保持一致：

```text
idle                待机循环
idle_variant        第二待机/呼吸/眨眼
tap                 大厅点击反馈
enter               登场
move                移动/冲刺
attack              普攻起手与收招
skill               技能施放
skill_loop          持续施法
hit                 受击
critical_hit        暴击受击
block               防御/护盾
heal                治疗
buff                增益
control             冻结/沉默/眩晕
poison              中毒
low_hp              低血量
victory             胜利
lose                失败
fall                倒地
revive              复活
level_up            升级
star_up             升星/突破
```

每个动画需要在 manifest 中记录 `unit、animation、duration、loop、event markers、fallback`。战斗事件使用 marker 触发伤害、音效、镜头和粒子，不能用任意 setTimeout 猜时间。

### 11.2 战斗表现

- 普攻：起手位移、武器轨迹、命中闪白、受击后仰、伤害数字、音效、短暂停顿。
- 技能：技能名卡、角色特写、屏幕遮罩、技能图标、轨迹/爆炸/治疗光环、命中反馈。
- 暴击：独立颜色、音效、镜头冲击、短暂 chromatic aberration 或径向闪光；减少动效时改为淡入。
- 护盾/治疗/中毒/冻结/沉默：头顶状态图标、持续粒子、状态消失反馈。
- 阵亡/复活：倒地、消散、召唤、复活光柱；禁止角色隐形后仍能行动。
- Boss：入场镜头、血条阶段、预警圈、蓄力、全屏技能和阶段转换。
- 结算：胜利姿势、奖励飞入 HUD、三星依次点亮、首次奖励高亮。
- 战斗速度：1×、2×、3× 和跳过必须同步动画、音效、计时器和事件，不改变最终结算。

### 11.3 大厅、剧情和菜单动效

- 大厅角色持续待机，点击有 tap 反馈，进入页面有出场动画。
- 导航按钮使用统一的按下、选中、返回、禁用状态；避免页面瞬间切换。
- 章节卡片支持解锁、选中、星级点亮、奖励预览动画。
- 剧情角色切换使用淡入/滑入；文本打字速度、自动播放和跳过必须可控。
- 招募使用召唤光束、卡牌翻面、稀有度颜色、SSR 特殊演出；十连结果可跳过但结果不能丢失。
- 升级/升星/装备使用统一的确认、进度、成功、失败和资源扣除反馈。
- 商店购买使用商品飞入钱包的反馈；任务领取使用勾选、进度补间和奖励飞入。
- 所有动效提供 `prefers-reduced-motion` 和游戏内“减少动效”双重降级。

### 11.4 动画技术约束

- Spine 负责角色骨骼和关键战斗动作；CSS/Canvas 负责 UI 和轻量特效；不要把大图序列帧全部塞进 DOM。
- 用 `AnimationEvent`/marker 驱动游戏事件；逻辑层只接收事件，不依赖帧时间猜测。
- 同屏角色和粒子有上限；进入后台暂停 rAF 和音频；资源按页面预加载并在离开页面释放。
- 低端设备提供静态首帧、降低粒子、关闭后处理、限制视频分辨率和音频并发。
- 动画验收必须包含：角色是否移动、动作是否在正确事件点命中、速度倍率是否一致、减少动效是否可用、Android WebView 是否掉帧。

## 12. 动画落地顺序

1. 建 `animation-manifest.json` 和事件 marker 命名规范。
2. 先完成 Kitty、Dominica、Florence 三个角色的全流程动作，作为 Vertical Slice。
3. 将战斗中的攻击/受击/技能/死亡从计时器改为 marker 事件。
4. 增加统一 `VfxService`、`CameraFxService`、`DamageNumberService`、`AudioCueService`。
5. 批量为其余角色补齐 idle、attack、skill、hit、victory、fall；缺动作的角色使用明确的 fallback。
6. 最后补大厅、抽卡、升级、任务、Boss 和结算动效，并做逐页录屏验收。

**动画完成标准：** 不是“页面上能看到 Spine”，而是每个主要玩法事件都有可见、可听、可跳过、可降级且与逻辑同步的反馈。
