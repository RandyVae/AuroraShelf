# Lust Goddess 案例深度实测审计

日期：2026-10-29  
审计对象：用户提供的 `https://www.lust-goddess.com/play?...` 公开 WebGL 案例  
审计方式：用户已打开案例后，由 Codex 通过 ChatGPT in-app browser 逐屏点击、截图和读取可见界面  
目的：把案例真正可见的叙事、镜头、角色表现、战斗教学和界面层级转化为原创卡牌游戏的制作约束

## 结论

案例的核心优势不是“开场直接出现战斗”，而是先建立角色和情境，再让玩家进入战斗。实测的开场是全屏剧情演出：暗场和近景角色图像、未知身份标签、逐句对白、轻触继续、跳过控制、双角色同框，随后才切入带教程的战术网格战斗。这个结构可以作为制作指南的叙事原型。

案例战斗在本轮可见范围内是回合制战术网格，不是本指南定义的 CCG。画面显示单位、攻击/生命数值、敌我阵营、回合数、格子选中和拖拽移动；本轮没有观察到牌组、抽牌堆、弃牌堆、手牌、能量费用或卡牌结算。任何交付若只做三人单位自动或网格战斗，都不能宣称已经完成“真卡牌游戏”。

## 证据边界

### Verified：本轮浏览器直接观察

| 阶段 | 可见事实 | 对制作的约束 |
|---|---|---|
| 开场黑场 | 黑色渐变/暗角覆盖大部分画面，角色以脸部和上半身近景显现；姓名先显示 `???`，对白用底部横线和短句呈现 | 先给情境和人物，再给系统 UI；第一帧必须有可读的主角焦点 |
| 角色唤醒 | 镜头从局部近景切到粉发通讯角色，背景为医疗舱/房间；对白由“队长？”、“队长！”、“睁开眼睛，队...”推进 | 角色表演要有镜头级构图变化，不能只换一张静态小图 |
| 身份揭示 | 角色名变为“凯蒂”，角色以大尺寸全身图站在场景中心；背景、角色和对白层次清楚 | 故事立绘应占据主要视口，姓名/身份在对白前可见 |
| 交互控制 | 右下持续出现“轻触以继续”；进入连续演出后右上出现“跳过”；底部有静音图标 | 故事必须支持点按推进、跳过、自动播放/静音，并把状态初始化与视觉跳过分离 |
| 双角色场景 | 切到街区俯视背景，凯蒂在左、持枪女性角色在右，双方同时占据左右主体区域；对白由其中一方继续 | 第一章至少安排两个可辨识角色或一个角色加无线电肖像，形成对话关系 |
| 战斗入口 | 剧情直接切到街区战斗场景，顶部显示双方阵营“伊桑 / 黑手党”，底部显示“回合 1”；敌我单位位于不同格子 | 叙事背景、阵营和战斗空间必须连续，切换要有明确的状态边界 |
| 战斗教学 | 教程文本解释敌人攻击和生命值，角色肖像位于右下；蓝色格子高亮和手形指引要求玩家选择格子/移动 | 新手教学应解释一个可执行动作，并在画面上高亮目标，不要只显示说明文字 |
| 回合推进 | 拖动单位后出现新单位和角色对白，回合变为“回合 2”；单位上方仍有攻击/生命数值 | 每个玩家动作都要产生可见状态变化、反馈和下一步目标 |

### Unverified：本轮没有把它当作事实

- 协议/付费/账号后的完整大厅、招募、养成、商店和任务循环。
- 案例是否存在真正的卡牌战斗、牌组编辑或卡牌奖励。
- 角色原生骨骼、Live2D、音频、语音、粒子和摄像机轨道的具体实现技术。
- 案例在 Android、低端设备、Reduce Motion、不同宽高比下的表现。

本轮曾看到成人向裸露画面。该内容只作为“内容分级与年龄门槛存在风险”的事实记录，不复制、提取或使用其素材；原创项目必须使用原创/已授权资源并设置自己的内容政策。

## 逐屏制作逻辑

### 1. 启动、内容门槛和预载入

启动画面要把年龄/内容分级、隐私和条款入口放在明确状态中，然后显示预载入进度、版本和重试状态。预载入期间应先展示自己的多角色主视觉或场景，不要让玩家面对空白画布。任何法律确认都必须有可测试的同意、拒绝和错误分支。

### 2. 序章剧院

序章不是一个 `setTimeout` 覆盖层，而是一条事件时间线：

```text
BOOT_READY
  -> SCENE_ESTABLISH（暗场、环境、镜头焦点）
  -> HERO_WAKE（近景/呼吸/眼神或轻微身体动作）
  -> IDENTITY_REVEAL（姓名、身份、第一句对白）
  -> ALLY_RESPONSE（第二角色或无线电肖像回应）
  -> CONTEXT_AND_OBJECTIVE（地点、威胁、任务目标）
  -> STORY_TO_BATTLE（背景与角色持续，切入战斗 HUD）
```

每个事件必须有 `id`、开始/完成/跳过信号、角色或背景资源、对白、音频 cue、VFX cue、时长和测试断言。跳过只跳过表现层，必须完成场景状态、任务目标、牌组种子和战斗初始化。

### 3. 角色美术和动画

故事角色使用长边至少 2048px 的透明全身/半身图或可授权的 Spine/Live2D 资产。故事视口的主角目标显示高度为 65%～80%；脸、武器和姓名牌不能被底部对白或顶部按钮遮住。最低动作集为 `idle`、`enter/wake`、`talk`、`react`、`attack`、`hit`、`victory`，并在 manifest 中把原生动作和合成回退分开记录。

“动”不等于只改变 `transform` 或 `opacity`。至少要能证明眼神/呼吸、姿态变化、镜头推拉或角色局部动作中的一项；技能和受击则需要 marker 驱动的命中时刻、音效、VFX 和数值反馈。

### 4. 故事到卡牌战斗

案例提供的是叙事到战术战斗的连续性；本项目要保留这种连续性，同时在战斗层实现真正的卡牌循环：20 张牌组、5 张起始手牌和一次 Mulligan、每回合抽 1 张、3～10 能量、抽牌堆/弃牌堆、敌方意图、目标合法性、状态效果和回放种子。角色立绘可以作为卡牌召唤或技能特写，但不能替代手牌和出牌决策。

战斗首屏必须同时呈现战场、手牌、能量、抽牌/弃牌计数、敌方意图和当前目标。打牌顺序为：预览目标 → 确认出牌 → 扣能量 → 播放角色动作/marker → 结算伤害或状态 → 进入弃牌/消耗区 → 检查胜负。

### 5. 大厅和元循环

本轮没有把案例大厅列为已验证事实，因此大厅按产品目标设计：主视觉角色、资源 HUD、章节 CTA、卡组、角色、招募、任务和设置。每个页面只有一个主动作和一个返回路径；角色详情需要大立绘、状态、升级/技能/装备和故事入口，卡组页面需要牌数、费用曲线、合法性和保存反馈。

## 与当前项目的差距

当前仓库的 v2.6 已有序章时间线、Spine manifest、VFX 和 Android 截图，但这些是本地实现证据，不能代替案例事实，也不能证明已经有真实卡牌战斗。结合本轮实测，下一轮验收应优先检查：

1. 首次进入第一章是否先经过完整序章剧院，再进入战斗，而不是单个短特写。
2. 序章是否至少有一个大尺寸主角、一个回应角色、三段以上镜头/对白事件和明确目标。
3. 故事跳过后是否能在不丢状态的前提下直接进入可操作的卡牌战斗。
4. 战斗是否真的出现手牌、费用、抽牌/弃牌、敌方意图和卡牌结算。
5. 胜利后是否先有角色胜利/战报余波，再进入星级、奖励和升级，而不是直接弹窗。
6. 桌面 390×844、412×915、1080×2340 和 Reduce Motion 是否都有截图证据；资源 manifest 是否包含来源、许可、哈希、显示尺寸和回退。
